# 2026 年 10 月复盘

Flowpocus 在 2026-07-30 加完服务端 Canvas Commands 和 CLI 之后停更了。2026-10-18 重新启动，这一轮共 19 个提交，改动了 90 个文件。

这篇文章记录这一轮改了什么，以及每个决定背后的原因。前三部分是常规翻新。第四部分是重点，讲多实例同步怎么从"用 Redis 广播"一步步走到"单 owner + 数据库租约 + fencing"。中间有过一次被指出的正确性漏洞，也有一次换数据库后差点复发的竞态。

## 一、工程基础

停更期间，依赖和工具链都落后了。先把地基补齐，后面的改动才有保障。

- **检查链条。** 升级 Biome 和 Knip。加上 Lefthook 钩子。提交前跑 Biome，commit-msg 强制英文 Conventional Commits，推送前跑 Knip 和类型检查。CI 按矩阵跑 Biome、Knip、类型检查、测试、构建五项，并检查 PR 里每个提交的信息。另外加了 Dependabot。
- **全量升级依赖。** pnpm 12、Node 24、TypeScript 7（原生版 `tsc`）、Hocuspocus 4、`@hono/node-server` 2。有两处刻意没升级。`ioredis` 留在 5.x，因为 Redis 扩展固定依赖 `~5.6`。`@types/node` 留在 24，和运行时的 Node 24 LTS 保持一致。
- **打包从 tsup 换到 tsdown。** tsup 已进入维护状态，它的作者推荐 tsdown。产物与原来一致，体积小了约 7%。
- **数据库包能被 Node 直接加载。** `pnpm start` 曾因为 ESM 的相对导入没有扩展名而崩溃。修法是给导入写上 `.ts` 扩展名，再用 tsconfig 强制只允许可擦除的 TS 语法，这样 Node 的类型剥离能直接运行源码。
- **UI 细节。** 按钮迁移到 Base UI。`clsx` 加 `tailwind-merge` 换成了 `cn`。深色模式下 React Flow 的控件和小地图之前是白色的，原因是主题设置的是 `--xy-*-default` 变量，被 React Flow 后加载的样式表覆盖了。改成设置不带 `-default` 的变量后就正常了。

## 二、让 agent 成为一等公民

Flowpocus 的定位是人和 agent 编辑同一张画布。这一轮把 agent 的入口补完整了。

- **MCP 端点。** 后端在 `/mcp` 提供无状态的 Streamable HTTP MCP 服务。工具包括 `list_canvases`、`get_canvas`（读取 live 的 Y.Doc），以及每条 Canvas Command 各对应一个工具。它们和 HTTP 路由走的是同一条服务端执行路径。
- **画布按 ID 路由。** 以前页面写死只能打开 showcase 画布，所以 agent 通过 API 新建的画布在浏览器里打不开。现在 URL 是 `/canvas/[id]`，ID 可以直接交给 agent。
- **短 ID。** 画布 ID 改成 12 位 base62，节点和边改成 8 位 base62。原来有四种各自为政的 ID 格式，现在统一由一个生成器产生。agent 收发的 payload 也因此更短。
- **AGENTS.md。** 改写成 agent 动手前必须知道的几件事，包括命令的归属、Yjs 绑定和命令幂等的不变量，以及要跑哪些检查。

## 三、存储

- **Yjs 状态存成二进制。** 以前是 base64 文本，每份快照凭空大约 33%，每次读写还要编解码一次。现在直接存二进制字节。
- **`version` 改成原子自增。** 原来的写法是先读出 version 再写回 version + 1，看起来像乐观锁，其实并不是，两个并发写入还会合并成一次自增。改成在 SQL 里自增。这里刻意没有做成乐观锁。`store` 每次拿到的是合并后的完整文档，冲突时拒绝写入反而会丢编辑。
- **DB 还是 S3 的决策笔记。** 实测了不同节点数下的快照大小，写在 [hocuspocus-storage.md](../future/hocuspocus-storage.md)。其中有一个反直觉的结论。Yjs 文档只增不减，每次覆盖写都会留下约 10 字节的墓碑。所以长期使用的画布，大小取决于历史总写入次数，而不只取决于当前内容。

## 四、多实例，从 Redis 到单 owner

这是这一轮花时间最多、也学到最多的部分。下面按实际讨论的顺序来写。

### 1. 起点是 Redis Pub/Sub

原来的多实例方案是 `@hocuspocus/extension-redis`。同一张画布可以同时在多个实例上加载，各实例之间通过 Redis Pub/Sub 广播 Yjs 更新。

### 2. PostgreSQL 的 LISTEN/NOTIFY 能替代 Redis 吗

理论上可以，实际上不划算。读了 Redis 扩展的源码后发现，它依赖三样东西。一是每个文档一个频道的广播，二是用 `PUBSUB NUMSUB` 判断有没有其他实例也打开了这个文档，三是用 Redlock 串行化写库。逐项对照 PostgreSQL 的结果如下：

- NOTIFY 的 payload 上限是 8000 字节，而且只能是文本。Yjs 的大更新和首次同步放不下。
- 所有 NOTIFY 在提交时争同一把全局锁，高频编辑会卡在这里。
- PostgreSQL 没有能查询跨会话订阅数的东西，`NUMSUB` 找不到对应物。
- 只有锁能直接替换，用 advisory lock 反而比 Redlock 更可靠。

结论是，用 PostgreSQL 换掉 Redis，并没有解决"同一份文档存在多个副本"这个根本问题。

### 3. 换一个前提，每张画布只放在一个实例上

与其想办法同步多个副本，不如从一开始就不产生副本。这个思路有不少成熟的先例。

- Figma 的多人协作服务器给每个文档起一个独立进程（[Figma 博客](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)）。
- Cloudflare Durable Objects 保证每个 ID 在全球只有一个实例（[官方文档](https://developers.cloudflare.com/durable-objects/concepts/what-are-durable-objects/)）。
- Hocuspocus 自己的扩展性指南也建议按文档标识拆分实例（[Scalability](https://tiptap.dev/docs/hocuspocus/guides/scalability)）。

不过只靠负载均衡做一致性哈希是不够的。扩缩容或者发布的时候，哈希环会变化，同一张画布可能短暂地在两个实例上同时打开，两边都会写库。所以正确性必须由别的机制来保证，哈希只能用来减少转发。

### 4. 落地为数据库租约加实例间转发

- 每张画布在 `canvas_leases` 表里最多有一行，记录 owner 实例和它的内网地址，以及过期时间。
- 加载文档前先抢租约。抢租约是一条 `INSERT ... ON CONFLICT DO UPDATE ... WHERE`。只有在没人持有、本来就是自己持有、或者原 owner 已过期这三种情况下才会写入。`RETURNING` 返回 0 行就说明没抢到。判断和写入在同一条语句里，两个实例同时抢的时候，数据库靠主键行锁把它们串行化。
- owner 每 `TTL/3` 续约一次，可以连续错过两次续约而不丢租约。续约失败时会断开本地的客户端。
- 不是 owner 的实例收到 WebSocket 连接时，原样转发给 owner。收到 Canvas Command 或 live 读请求时，调用 owner 的 HTTP 接口。客户端无论连到哪个实例都能正常工作。

这样做的直接收益有三个。一张画布只有一个副本，只有一个实例会写库。command 的幂等记录只有一个来源。加载文档时不再需要等其他实例回传状态。

### 5. 把 Redis 保留为可选模式

后来又做了一层抽象，把 Redis 也做成可选项。抽象后发现 Redis 模式其实很简单。所有实例都认为自己是 owner，不需要转发，再挂上 Redis 扩展就行。它只是同一个 `CanvasPlacement` 接口的另一个实现，代码不到 50 行。现在用 `CLUSTER_MODE=owner|redis` 切换。

什么时候该切回 Redis，[ADR 0001](../adr/0001-single-owner-placement.md) 里列了条件。主要有三种情况。单张画布的负载超过一个实例能承受的范围。实例之间网络不通。不能接受 owner 切换时客户端重连。

### 6. 被指出的漏洞，先检查后写入

第一版的写法是，写库前先调用 `holds()` 确认租约还在，然后再执行 UPDATE。另一个 agent 审查代码时指出，这两步之间有空隙。

真正会丢数据的时序是这样的：

1. 旧 owner A 检查租约，结果是还在。
2. A 卡住了，比如遇到 GC 停顿或事件循环被阻塞，持续时间超过了 TTL。
3. B 接管画布，写入新的编辑，然后卸载文档。
4. A 醒过来，把旧状态写进库里。B 已经不会再写了，所以 B 的编辑永久丢失。

我最初在 ADR 里写的是"这个窗口极小，而且新 owner 下一次写库会把它覆盖掉"。这个说法不对，新 owner 不一定还会有下一次写库。更关键的是，owner 丢租约最常见的原因恰恰就是卡在某个地方，所以这个窗口不能当作"极小"来看待。

修法叫 fencing，就是把租约条件直接写进写库语句本身。

```sql
UPDATE canvases SET ...
WHERE id = $1
  AND EXISTS (SELECT 1 FROM canvas_leases
              WHERE canvas_id = $1 AND owner_id = $me
              FOR SHARE)
```

失去租约的实例写库时匹配不到任何行，只记一条告警。它的客户端重连后，会把本地的编辑同步给新 owner。CRDT 在这里帮了大忙。客户端本地就有完整的文档，所以即使服务端拒绝了旧 owner 的写入，编辑也不会丢。仓库里有一个测试，专门复现上面这个时序。

### 7. 换成 PostgreSQL，差点复发

当时的数据库还是 SQLite。SQLite 会把所有写操作串行执行，单条语句里的子查询和 UPDATE 之间不会被插队，所以上面的 fencing 是成立的。

切到 PostgreSQL 后情况变了。在默认的 READ COMMITTED 隔离级别下，子查询读的是语句开始那一刻的快照。如果此时 B 的接管正在提交，A 的子查询看到的仍然是"我是 owner"，于是照常写入。`FOR SHARE` 的作用是让 A 先等 B 的接管提交完成，再按最新的 owner 重新判断。

验证方法是，测试先开一个不提交的接管事务，再让旧 owner 去写库。加了 `FOR SHARE` 时，写库会等待，最后匹配不到行。去掉 `FOR SHARE` 再跑一次，写库立即成功，测试失败。所以这个竞态是真实存在的，不是理论上的担心。

### 8. 用数据库的时钟

一开始，租约的过期时间是用各实例自己的时钟计算的。如果实例分布在多台机器上，时钟偏差会导致过早或过晚接管。现在所有过期时间都写成 `now() + ttl`，判断过期也和 `now()` 比较，统一用数据库的时钟。测试也不再注入假时钟，而是直接在数据库里把租约改成已过期。

### 9. TTL 为什么是 30 秒

坦白说，这个数是按经验选的保守默认值，没有经过测量。它在权衡两件事。TTL 越长，实例崩溃后画布不可用的时间越长。TTL 越短，越容易把还活着但暂时卡顿的 owner 误判为失效，导致客户端频繁断开。正确的定法是测出两个值。一个是续约耗时和事件循环停顿的 p99，另一个是产品能接受的不可用时长。

还有一个实测结果值得记下来。在丢租约的端到端测试里，从断开到重新同步超过了 30 秒，大部分时间花在客户端 `HocuspocusProvider` 的重连退避上，而不是 TTL 本身。所以只调小 TTL，并不能等比例地缩短恢复时间。

## 五、学到的东西

- **问题的前提值得先质疑。** "能不能用 PostgreSQL 替代 Redis 做广播"这个问题，真正的答案是"不需要广播"。
- **先检查后写入，在分布式环境里几乎总是错的。** 条件要放进写操作本身。租约只能保证"大部分时间"只有一个 owner，fencing 才能保证结果正确。
- **同一句 SQL，换个数据库语义就变了。** 在 SQLite 上正确的 fencing，到了 PostgreSQL 的 READ COMMITTED 下需要加 `FOR SHARE`。只换驱动不跑并发测试，这个漏洞会悄无声息地回来。
- **测试要能在代码错误时失败。** 并发测试是先确认"去掉 `FOR SHARE` 会失败"之后才算数的。
- **CRDT 改变了故障恢复的思路。** 客户端本地有完整的文档，所以服务端可以放心地拒绝可疑的写入。
- **默认值也要说清楚来历。** 30 秒是经验值，这一点写进了文档，以后有数据时就知道该改哪里。
- **另一双眼睛很有用。** fencing 漏洞就是靠另一个 agent 审查代码发现的。
